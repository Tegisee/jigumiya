# 가격 체커 Cron 설계 문서

## 1. 현재 문제
- 단일 사이클만 실행되는 설계 버그 (cyclesPerDay 계산만 하고 루프 미구현)
- 하루 1회 가격 체크만 되고 있는 상태

## 2. 제약 조건
- GitHub Actions 단일 job 최대 6시간
- Rate Limit: 분당 최대 40회 호출
- Block zone: 01:00~04:30 KST (카테고리 업데이트 보호)
- Block zone 실측 점유: 02:44~03:46 KST (GitHub 지연 44~81분 포함)
- 가용 시간: 24h - Block zone 3.5h = 20.5시간 (1,230분)

## 4. 시간대 분산 배치 설계 원칙
- 피크 시간대(07:00~23:00) 집중 배치
- 심야(23:00~01:00) 최소화
- 새벽(04:30~07:00) Block zone 후 재개
- Block zone(01:00~04:30) 자동 회피

## 5. 쿠팡 이용자 피크 시간대 구간 정의
- 출근 준비/출근길: 07:00~09:00
- 오전 휴식: 10:00~11:00
- 점심 피크: 11:30~13:30
- 오후 휴식: 15:00~16:00
- 퇴근길: 17:00~18:30
- 저녁 최대 피크: 19:00~22:00
- 취침 전: 22:00~23:30
- 심야: 23:30~01:00
- 새벽(Block zone 후): 04:30~07:00

## 7. 향후 구현 방향
- N값 자동 감지 → cron 간격 자동 선택
- 피크 시간대 가중치 배치 자동화
- 아이고 활성화 시 Block zone 재검토 필요
- N > 13,200 케이스: 추후 검토 (split 모드 + 별도 설계)

## 8. 임시 운영 방침
- 현재(N=37): 매시간 cron으로 임시 운영 예정
- N=400 도달 시: 10분 간격으로 전환
- N=600 도달 시: 15분 간격으로 전환
- N=800 도달 시: 20분 간격으로 전환
- N=1,200 도달 시: 30분 간격으로 전환
- 이후 N값 증가에 따라 단계적 조정

## 9. 아이고 활성화 시 Block zone 재검토
- 아이고 cron 6개 활성화 시 Block zone 01:00~04:30 빡빡해짐
- GitHub 지연 44~81분 감안 시 Block zone 끝을 04:45 또는 05:00으로 확장 검토
- 또는 Block zone 폐기 후 간격 sleep으로 충돌 회피 방식으로 변경 검토

## 10. 공유상품 중복 효과 (N값 증가 둔화)
- 사용자가 늘어도 같은 상품을 여러 명이 추적하면 `shared_products`에는 1개 문서만 존재
- API 호출은 unique 상품 수(N) 기준 → 사용자 수와 N이 비례하지 않음
- 예시: 사용자 1,000명 × 각 20개 추적 = 20,000개 추적이지만 인기 상품 중복 고려 시 실제 N = 500~1,000개 수준 예상
- 이것이 Phase 3 shared_products 설계의 핵심 목적
- 사용자가 늘수록 N 증가 속도가 둔화되는 구조 → §3 cron 간격 전환 시점이 예상보다 늦어질 수 있음
- 단, 중복을 강제할 수 없으므로 자연 발생 중복(인기 상품, 카테고리 베스트)에 의존

## 11. 자동화 설계 (B안) — N값 기반 실행 타이밍 자동 결정

### 핵심 아이디어
- yml: **10분 고정 트리거** (가장 짧은 간격의 공약수)
- 코드 실행 시마다 N값 읽기 → 최적 cron 간격 결정 (§3 매트릭스 기준)
- cyclesPerDay 계산 → 하루 총 사이클 수 결정
- 피크 시간대 비중 배분 (§5 기준) → 피크에 더 많은 사이클 배치, 심야 최소화
- **"지금 내 차례인가?"** 판단 로직 → 아니면 즉시 종료 (graceful exit)
- yml schedule 변경 없이 코드만으로 N값 성장에 자동 적응

### 동작 예시

| N값 | 시간대 | 적용 간격 |
|-----|------|---------|
| 37 | 피크 (07:00~23:00) | 10분 |
| 37 | 심야 (23:00~01:00) | 1시간 |
| 1,200 | 피크 | 30분 |
| 1,200 | 심야 | 2시간 |
| 1,800 | 피크 | 45분 |
| 1,800 | 심야 | 3시간 |

피크 간격은 §3 매트릭스 그대로, 심야는 2~3배 확장.

### 구현 순서

1. **yml schedule 변경**: `'*/10 * * * *'` (10분 고정 트리거)
2. **main() 시작 시 N값 fetch** (`shared_products` 풀 length)
3. **N값 → 최적 간격(intervalMinutes) 결정** (§3 매트릭스 룩업)
4. **현재 시각이 피크/비피크 판단** (§5 정의 기준 KST hour)
5. **간격 결정**: 피크면 `intervalMinutes` 그대로, 비피크면 `intervalMinutes × 2~3배`
6. **lastRunAt 확인** (`meta/stats.lastRunAt` 저장값) → `now - lastRunAt < intervalMs`면 즉시 graceful exit
7. **간격 충족이면 정상 실행** → 완료 후 `lastRunAt = now` 갱신

### 의사 코드

```typescript
const N = shared_products.length;
const baseInterval = lookupBaseInterval(N); // §3 매트릭스
const isPeak = isPeakHour(getKstHour());    // §5 기준
const interval = isPeak ? baseInterval : baseInterval * 2;
const lastRunAt = await readMetaStats('lastRunAt');

if (Date.now() - lastRunAt < interval * 60 * 1000) {
  console.log(`[Skip] interval=${interval}min not yet`);
  return; // graceful exit
}

await runCycle();
await writeMetaStats({ lastRunAt: Date.now() });
```

### 장점
- yml 한 번 설정 후 N값 성장에 자동 적응 (수동 schedule 변경 불필요)
- 피크/심야 차등 배치로 사용자 체감 갱신 빈도 ↑ + 호출량 효율화
- §3 매트릭스에 단계 추가 시 코드만 갱신 (yml 무수정)

### 단점 / 고려사항
- 10분마다 runner 기동 비용 (Public 레포 무제한이라 무료지만 noise log 증가)
- `meta/stats.lastRunAt` 새 필드 필요 (기존 `lastCheckedOffset`과 별개)
- Block zone 가드 + 간격 가드 두 단계 graceful exit 흐름 → 로깅 명확화 필요
- 첫 실행 시 `lastRunAt` 없음 → undefined 처리 (즉시 실행으로 fallback)
- 룩업 테이블 변경 시 즉시 효과 — 의도치 않은 burst 방지 위해 PR review 필수
